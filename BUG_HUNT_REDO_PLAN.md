## Part 1 — Decisions needed first

These shape several items below.

**D1. Failure handling in event processing — decided.** On any failure while processing a message: no ack, no nack;
log an ERROR naming the message and the exception; wait with capped exponential backoff (1s, 2s, 4s … ~60s); process
the same message again; never move past it until it succeeds. Transient failures recover by themselves without losing
order; bugs keep failing loudly (bounded by the backoff) until a fix is deployed, and the redeploy's resubscription
redelivers from that message. The rest of the service keeps running; cancellation (shutdown) stops retrying at once.
Implementation: remove `acknowledgeAsFailed` (swissknife contract, Pulsar `negativeAcknowledge` impl, test spy);
`processAsCompositeEvent` lets exceptions propagate (no `runCatching`); remove `EventProcessingResult.Failure` if
nothing else needs it; pillar `MessagingEventProcessor` gets the retry loop, covering failures anywhere in the
per-message path (not only inside handlers).

**D2. Invocation-context header encoding (10.1) — decided.** The header carries the context as base64url (no padding)
of its UTF-8 JSON: commas in JSON make headers legally splittable/mergeable by proxies and clients (and non-ASCII
doesn't belong in headers), which is what the old comma-join worked around. Writer: pillar `withInvocationContext`;
reader: pillar `GatewayInfoContextParsingFilter` decodes a single value — invalid base64/JSON or more than one header is
a 400. Header description updated in both services' `api.yaml`. The gateway stub is left untouched. Verified first: with
http4k 6.61 on JettyLoom a raw JSON header currently arrives as one entry, so this is robustness, not a live outage.
