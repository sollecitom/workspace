# Workspace scripts, aggregator, gradle-plugins

## Workspace root

**High**
- `scripts/cleanup-docker-images.sh:80-84`: images are ranked by `.Created`, but every Jib image is built reproducibly and has `Created = 1970-01-01`. I saw this on every local `ghcr.io/sollecitom/*` image. With all ties, `sort -r` falls back to ordering by image ID, so "keep newest 2" keeps 2 arbitrary images. Scenario: three builds produce IDs `sha256:9…`, `sha256:5…` and `sha256:1…` (the current one, tagged `latest` and HEAD). Cleanup keeps the two old images and runs `docker image rm` on the current `:latest` and HEAD tags. Separately, `rm` of a tag still used by a container fails under `set -e` and stops the whole workspace pipeline. Confidence: confirmed (the abort case is plausible). Fix: rank by `{{.Metadata.LastTagTime}}` from `docker image inspect` instead of `.Created`.
- `scripts/cyclonedx-init.gradle:307-313` and `352-358`: the two aggregate tasks only declare root build files as inputs, not the per-project snapshot or BOM files. Scenario: a dependency is added in a subproject's `build.gradle.kts` (version already in the catalog). LicenseAudit sees the change and reruns Gradle. The per-project snapshot is regenerated, but `aggregateLicenseDependencySnapshot` is UP-TO-DATE. The audit then reads the stale `dependency-snapshot.json` and misses the new dependency (removed dependencies also linger). The per-project inputs (`:42-82`) have the same gap: they also miss `buildSrc/**/*.kt` and the build files of projects it depends on. Confidence: confirmed. Fix: `inputs.files(workspaceRoot.allprojects.collect { directSnapshotOutputFileFor(it) })`, and the same for the BOM.
- `scripts/workspace.sh:220-228`: the Gradle lock-retry never runs for `update`, `update-internal` or `publish`. Those callers (`:680`, `:697`, `:758`) are not inside an `if`, so under `set -e` a non-zero return at `:220` exits the script before the `grep` at `:223`. Only the build/rebuild callers (inside `if`) get the retry. Confidence: confirmed. Fix: `run_command_with_live_logging "$shell_command" "$log_file" && exit_code=0 || exit_code=$?` at both call sites.

**Medium**
- `scripts/workspace.sh:913-923,1071-1073` with `scripts/ensure-workspace-requirements.sh:75-78`: any `execute` that includes `build`, `publish` or `pull` runs `brew upgrade just jq` and `brew upgrade --cask temurin`. So the daily `build-workspace` loop can switch the machine JDK to a new major, since the `temurin` cask tracks the latest one, and may prompt for sudo. README:12,24 says this only happens during install/update. Confidence: confirmed. Fix: call `ensure_workspace_requirements check` unless the steps include `update`.
- `scripts/workspace.sh:516-526` vs `:680-683`: the "Java image fallback" event is written during `build`, after the `update` step has already collected the summary. Scenario: the base image moves 25→26, the build fails, and the fallback keeps 25. The final UPDATE SUMMARY still says "Java image: 25… → 26…" and never mentions the fallback. Confidence: confirmed. Fix: re-collect the summary for that module after a fallback build, or print the event file at the end.
- `scripts/workspace.sh:313-333,346`: the script pins the digest of a single-platform manifest (arm64 on Apple Silicon) into the committed `gradle.properties`/Dockerfile, rather than the multi-arch index digest. A build on linux/amd64 then gets an arm64-only base image. The error text at `:342` also always says "linux/amd64". Confidence: plausible (only bites builds on other platforms). Fix: pin the index digest (`docker buildx imagetools inspect "$image" --format '{{.Manifest.Digest}}'`).
- `scripts/workspace.sh:1192-1202` (`just reinstall-workspace`): runs `rm -rf` on every repo with no check for uncommitted changes or unpushed commits, then re-clones from GitHub. Scenario: local WIP commits that `pull` created but never pushed are lost permanently. Confidence: confirmed. Fix: refuse when `git status --porcelain` or `git log @{u}..` is non-empty.

**Low**

Unlike `run-license-audit.sh:13-33`, it ignores newer sources, so workspace audits run old `LicenseAudit.kt` logic after edits. Confidence: confirmed. **Critical**

# element-service-example — http-event-bridge

## http-event-bridge: bug hunt findings

Note on the cut-off: the API outage hit after I had read the slice; no files were left unread.

### module/implementation + application/model

**High**

- `application/model/.../ApplicationImplementation.kt:28` (with `endpoint/.../CompliancePlanEventEndpoint.kt:23-27`). **Defect:** the client-supplied `event.metadata` (event id, timestamp and the full invocation context: actor, customer, tenant, roles, trace, external invocation id) is published to Pulsar as-is. The authenticated request context is ignored. **Scenario:** an authenticated user POSTs an event whose `metadata.context.invocation.access` names another account or customer with elevated roles. Downstream consumers fork their context from that forged identity, and the lifecycle notification republishes it. `HttpEventBridgeModuleTestSpecification.kt:67,94` even asserts this behaviour (`hasInvocationContext(event.context.invocation)`). **Confidence:** confirmed. **Fix:** rebuild the event metadata from the request's `InvocationContext` (new id and timestamp) and keep only `data` from the body.

- `endpoint/.../CompliancePlanEventEndpoint.kt:23`. **Defect:** the only check is "authenticated" (`toAuthenticated`). There is no role/service check, and the plan's `customer` is never compared with the caller's customer. **Scenario:** any logged-in end user (the api.yaml example uses role `user`) can inject a fake `standards-analysis-completed` or `requirements-analysis-completed` event for any customer's plan, which also triggers that customer's notifications. **Confidence:** confirmed. **Fix:** require a service/ingestion role and reject when `compliancePlan.customer` differs from the authenticated customer.

**Medium**

- `module/implementation/.../HttpEventBridge.kt:45-48`. **Defect:** shutdown order is wrong. The connector (consumer and producer) stops before the processor that is still consuming and acking through it. **Scenario:** a message being processed at shutdown fails its notifier publish or ack against a closed client. The message is redelivered and a duplicate notification goes out. **Confidence:** confirmed. **Fix:** stop in reverse start order: processor, then connector, then lifecycle publisher.

- `application/model/.../ApplicationImplementation.kt:40-48`, caused by a shared API (swissknife `CompositeEventProcessingUtils.processAsCompositeEvent` uses `runCatching`). **Defect:** `CancellationException` (and `Error`) are caught and turned into `EventProcessingResult.Failure`. **Scenario:** during `processing.cancelAndJoin()`, a notifier publish suspended mid-flight becomes a Failure, and the loop then calls `acknowledgeAsFailed()` inside a cancelled coroutine. **Confidence:** plausible. **Fix:** rethrow `CancellationException` in `processAsCompositeEvent` (shared fix).

- `application/model/.../ApplicationImplementation.kt:28`. **Defect:** there is no idempotency. The client-chosen event id is never deduplicated, and producer dedup is not enabled (`defaultProducerCustomization`). **Scenario:** a client retries after a timeout and the same event is published twice. Downstream "outputs available" handling runs twice and duplicate notifications are sent. **Confidence:** plausible. **Fix:** dedup on event id (Pulsar broker dedup with sequenceId from the event id, or a processed-id check).

**Low**

- `endpoint/.../CompliancePlanEventEndpoint.kt:29`. **Defect:** the response is always `200 OK`, even when the result is `ApplicationResult.Error`. **Scenario:** if `Error` is ever returned (the type allows it, though nothing returns it today), clients and gateways treat the failure as success. **Confidence:** confirmed (latent). **Fix:** map `Error` to a 5xx or 422 status.

- `endpoint/.../CompliancePlanEventEndpoint.kt:25`. **Defect:** `$arguments` resolves to the companion's body lens, because the local `arguments` is declared on the next line. **Scenario:** every request logs the lens object's `toString` instead of the request arguments. **Confidence:** confirmed. **Fix:** move the log line after `val arguments = arguments(request)`.

### adapters/driven/email-notifier

**High**

- `.../notifier/StandardsOutputsAvailable.json` and `RequirementsOutputsAvailable.json` (vs `serialization/StandardsOutputsAvailableJsonSerde.kt:18-22` and `RequirementsOutputsAvailableJsonSerde.kt:18-22`). **Defect:** the published schema requires the flat fields `compliance-plan-id`, `compliance-plan-owner-id` and `organization-id` with `additionalProperties:false`. The serde writes a nested `compliance-plan` object and none of those fields. **Scenario:** every message on `compliance-plans-lifecycle-json` violates its declared contract, so an email consumer built from the schema rejects or misparses all of them. It is not caught because the Pulsar schema is `Schema.STRING` (no validation) and the email-notifier module has no serde or schema-compliance tests. **Confidence:** confirmed. **Fix:** make the serde emit the schema's fields (or fix the schema) and add an `AcmeJsonSerdeTestSpecification` for both types.

**Medium**

- `PulsarCompliancePlanLifecycleNotifier.kt:22`. **Defect:** `publisher.publish(event)` drops the triggering message's id. The `ReceivedMessage` context is never passed through the notifier interface, so parent and originating ids are null. **Scenario:** lifecycle notifications look like originating messages and causal lineage to the triggering message is lost. The module test never checks `isOriginating` on the notification. **Confidence:** confirmed. **Fix:** thread the parent message through and use `publish(event, parent)` / `publishWithParentMessageContext`.

**Low**

# element-service-example — compliance-plans-viewer

## compliance-plans-viewer: bug hunt report

### adapters/driven/repository/postgres

**Critical**

- `PostgresCompliancePlansRepository.kt:48`: The client-supplied `continuation-token` is pasted straight into the SQL (`AND pk > ${it.value}`). Nothing validates it: `PaginationArguments.json` only requires `minLength: 1`, the http4k lens does no schema validation, and `Pagination.Arguments` has no checks. **Failure:** a request with `"continuation-token": "0 OR 1=1"` produces `WHERE customer_id='A' AND state_type IN (...) AND pk > 0 OR 1=1`. That returns every customer's plans. Even the ULID token shown in the OpenAPI example (`01J91MBZ...`) causes a SQL syntax error and a 500. Lines 44 and 48 also interpolate `customerId`, and `Id.fromString` falls back to `StringId` for any string, so a quote in a customer id is another way in. **Confidence:** confirmed. **Fix:** use bound parameters (`.bind("token", it.value.toLong())`, `.bind("customer", customerId)`, a states array with `= ANY(:states)`) and reject tokens that aren't numeric with a 400.

**High**

- `PostgresCompliancePlansRepository.kt:42`: The tenant comes from `context.customerOrNull`, which returns `specifiedTargetCustomer ?: actor.customer`. In pillar's `GatewayInvocationContextFilter` (`parseSpecifiedTargetCustomer`), `specifiedTargetCustomer` is taken from the `x-<company>-specified-target-customer-id` request header, and nothing checks the caller is allowed to use it. **Failure:** any authenticated user sets that header to another customer's id and reads their plans. The endpoint (`toAuthenticated`) and the repository do no authorization check of their own. **Confidence:** plausible (whether it's reachable depends on the gateway being the pillar filter). The shared API is at fault too. **Fix:** scope reads to `authenticated.access.actor.customer`, and only honour a target customer after a role/authorization check.

- `PostgresCompliancePlansRepository.kt:115`: The upsert's `ON CONFLICT ... DO UPDATE` always overwrites `state_type` and `state_payload`, with no check that the stored state is older. **Failure:** a `StandardsOutputsAvailable` that failed is nacked (`acknowledgeAsFailed`) and redelivered after `RequirementsOutputsAvailable` was already applied. The plan then goes back from RequirementsReady to StandardsReady, and the view stays wrong for good. **Confidence:** confirmed (mechanism). **Fix:** add `WHERE (Compliance_Plan.state_payload->>'order')::int <= (EXCLUDED.state_payload->>'order')::int`, or an equivalent order/`reachedAt` guard.

- `PostgresCompliancePlansRepository.kt:49-57,62`: Pages are fetched with `ORDER BY pk` and `LIMIT`, then sorted by state in memory, and the continuation token is the pk of the last row *after* that sort. **Failure:** the requested sort only applies inside each page, not across the result. The token's pk can be lower than other pks on the page, so the next `pk > token` page returns rows already served (duplicates). The spec only checks ordering within a page, so it can't catch this. **Confidence:** confirmed. **Fix:** sort in SQL (`ORDER BY state_order <dir>, pk`) with a composite keyset token, or emit `records.maxOf { it.primaryKey }` and drop the in-memory sort.

**Medium**

- `PostgresCompliancePlansRepository.kt:50,62`: `limit` is never validated. **Failure:** `limit: 0` returns no rows, then `records.size < 0` is false and `records.last()` throws `NoSuchElementException`, giving a 500. A negative limit is a Postgres error and a 500. A very large limit is an unbounded scan. **Confidence:** confirmed. **Fix:** require `limit in 1..MAX` and return a 400 otherwise.

- `PostgresCompliancePlansRepository.kt:43`: An `equal-to` selector with `"selected-states": []` (the schema has no `minItems`) produces `state_type IN ()`, a SQL syntax error, so a 500. **Confidence:** confirmed. **Fix:** add `minItems: 1` to `EqualToSelector.json` and short-circuit an empty state set to an empty page.

- `PostgresCompliancePlansRepository.kt:115`: The conflict update never sets `device` or `device_id`. **Failure:** when a later event carries a renamed device, the view keeps serving the old device name. **Confidence:** confirmed. **Fix:** add `device_id = EXCLUDED.device_id, device = EXCLUDED.device` to the `SET`.

**Low**

- `PostgresCompliancePlansRepository.kt:59-62`: When the rows left exactly equal `limit`, a continuation token is still returned. The client then fetches an extra page that is always empty. The count and the page also come from two separate queries outside a transaction, so `totalItemsCount` can disagree with the items. **Confidence:** confirmed / plausible. **Fix:** fetch `limit + 1` rows to decide whether a next page exists, and run both queries in one read-only transaction.

- `PostgresCompliancePlansRepository.kt:42`: A null customer becomes the literal `customer_id = 'null'`. **Failure:** an authenticated context with no customer gets an empty 200 instead of being rejected. **Confidence:** confirmed. **Fix:** use `customerOrThrow()` and map that to 403.

- `PostgresCompliancePlansRepository.kt:101-110`: `upsertAll(emptyList())` executes a statement with no bound parameters, so R2DBC throws. **Confidence:** plausible. **Fix:** `if (plans.isEmpty()) return`.

- `DocumentModule.kt:30-32,77`: For an `InMemoryDocument`, the serializer writes `value.name.value` into `format_name`, `format_extension` and `format_mimetype`. **Failure:** reading it back throws "unsupported format". The error message on line 77 also prints the deserializer object instead of the extension. Nothing persists documents today, so this can't be hit yet. **Confidence:** confirmed (currently unreachable). **Fix:** write `value.format.name.value`, `value.format.extension` and `value.format.mimeType`.
